# 连续原始运行轨迹与正常战斗时序修正

本轮让原始25个系统在无界面环境连续运行，并据此修正了**正常网页战斗**中的发波、敌人插入、建塔和移动步长。统一实体编号及全局主脚本/伤害/粒子调度仍未完整接入，3-2仍未验收。

## 原始运行采集的范围

`export_native_level_runtime.lua` 每例启动独立beta3执行器，通过 `export_level_entity_bootstrap.lua ... runtime` 执行原始 simulation.init/do_tick、关卡、波次、主脚本、SSO、伤害、粒子、动画帧更新及插入/删除回调。与上一轮仅执行首次插入不同，这里保留全部update阶段。遇到原始paused即停止，不再在败局暂停后继续强行do_tick。

测试场景是第三关铁人、难度2、明确的entry测试存档：两条既有通关记录、原始模板中的0经验杰拉尔德/泽菲拉、未购买升级。原始player_level结果为2。它不是视频里的完整玩家配置，不把视频的未知英雄技能、经验或全局升级当作已知输入。

`native-runtime-smoke-input.json` 在第31/61/91tick分别建造7/4/5号投石塔，第121/151tick建造6/10号法师塔，第181tick发波。建造通过写入原GUI同样的tower.upgrade_to，发波写send_next_wave；原系统自己处理价格、施工、替换和生成。没有注入伤害、额外金币、敌人血量或通关结果。

`native_runtime_resources.lua` 使用原始 A.load、EXO.load/load_groups 和原始动画/骨骼定义。图像查询提供原始图集的size/trim及逻辑参考缩放，默认1像素图由原方法构造元数据；GPU图像/Quad句柄为空替代。组集合由明确的关卡/装备fixture构成，目录枚举使用主机排序，不声称复现Android资源加载器的所有顺序。两例没有缺失图像元数据或动画。声音仅执行原始元数据初始化和排队，**没有**播放器更新、音频文件选择或真实声卡，不能据此证明全局音频随机流或画面一致。

两种随机环境分别为原math.randomseed1234及固定连续值0.5（整数调用按原区间取中间值），不是拿一串观察结果替代游戏逻辑。导出器记录创建源行、当前系统、原始排队/插入/删除及逐tick实体表/队列/生命/金币/波次。原始协程可能把错误记入日志后停止，因此driver同时检查退出状态和错误/traceback日志，避免把部分停摆的执行当成有效轨迹。

两例共2782tick、3714事件。`verify_native_level_runtime.mjs` 从空Lua数字表应用原始事件，重建全局ID、真实入表顺序及count/max；包括只分配但不入表的damage，以及FX、地面贴花、塔弹、粒子等。这是事件重建验证，不是TypeScript已经实现所有原始控制器的证明。

## 已接入正常玩法的修正

### 发波和敌人入场

GUI调用只排队发波标志，波次系统在下一个simulation tick消费；重复点击在标志消费前被抑制，按钮立即隐藏。原版wave_spawn在系统更新阶段创建敌人，此时本tick的插入处理已完成，所以对象到下一tick才进入战场。

GameSession现在有相同的待插入边界，待插入敌人也阻止错误的提前胜利。WaveRunner的正常战斗路径改为原始逐tick等待：`utils.y_wait149–159` 在 `currentTime-startTime >= duration` 时结束，后续等待从实际恢复tick开始。不能把多个等待压在解析的理想时间线上，也不能用epsilon把边界提前。离线批量时间线接口仍保留原有连续时间分析模式，GameSession明确使用native tick模式。

初版误把y_wait当成严格大于，前12个出生恰好匹配，但4秒间隔暴露了一帧偏差。读取原始ISGE字节码后修正，没有改TSV的生成间隔。

### 施工和成塔

GUI输入后，原tower_upgrade阶段排队施工实体，下一个插入处理才显示施工。因此开始时间是输入时当前tick加2。原build脚本等待 `time-start > build_duration`（与通用y_wait的边界不同），随后请求升级，再到下一次插入处理才启用成塔。

TowerSystem现在保留施工开始及成塔排队时间，WorldRenderer在施工真正插入前继续画地基，施工动画从正确开始时间计时。没有通过增加建造时长常数来凑结果；不同起点上的浮点边界仍按原始减法判断。

### 固定移动步长

敌人移动改为原始 `tick_length * max_speed`。旧代码用相邻elapsed age相减计算distance，抵消误差会在 `distance-to-node < 2*step` 的精确边界改变nav_path.ni。独立原始行走检查检出一个位置仅差约2e-13、节点编号却不同的案例；使用固定步长后恢复零差异，没有放宽节点断言。新入场的首次动作也执行一个完整tick步长，首帧动画年龄为0。

## 对照与回归

`verify_native_spawn_queue.mjs` 在同一建造/发波输入和固定0.5环境中，实际执行GameSession1390tick，对齐36个原始敌人的类型、道路/支路/节点、入场tick及首次移动；另有1061个出生后一秒内的连续行走样本。五个建造地点逐tick比较地基→施工→成塔的真实原始状态。它没有使用观察到的出生顺序来驱动GameSession。

已有投石/法师开局的同输入原始协程对照重新采集，分别7354个独立行走样本均零差异。这些旧对照仍预设演员状态，因此不拿它们代替上述连续原始运行或整局验收。

部分旧测试假定GUI发波同步执行、0.833秒即成塔或在波次阶段之前就能施法。测试已改为等待真实阶段，并保留新的“发波输入本身不解锁法术”断言；法术控制器对照的独立时间起点也相应移动。没有删除成本、冷却、经验或教程断言。首次Node参数属性语法及渲染局部类型推断错误已修正。

原始完整导出、受影响的开局重新采集/原始导出、全量npm test及生产构建通过。`test:native-queue`通过正常界面建塔/发波，捕获真实渲染地基/施工/成塔和可见敌人，验证下一tick插入且无页面错误；新截图已检查。wave-flags、完整新手教程及刷新存档回归也通过，存档行为保留。

## 仍存在的差异

固定环境运行中，首发法球仍是网页507tick、原版508tick；第584tick网页金币75、原版70。生命归零所在tick目前一致，但网页结束判定与原版level阶段的暂停仍差一帧。伤害、全局执行顺序及全部随机消费者还没对齐；不能把出生/施工通过说成整局通过。

重新执行视频开局观察：video-bar-mid、seed104、场景13.5、输入窗口中点下，第77秒网页75金、观察90金，11号法师塔仍因金币不足被拒绝。其他玩家配置和输入边界仍未确定，没有调整数值抹平15金差异。

当前自然策略六流程结果为1-1胜20命、1-2胜1命、2-1胜20命、2-2败、3-1胜9命、3-2败（109.6333秒）。仍四胜两败；这是特定策略探测，不能当作视频验收。统一全局编号/执行阶段、多弹变化随机分配、C及其他技能、启动与完整视听验收仍需继续。
