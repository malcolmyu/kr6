# 英雄近战到位后的等待

本轮修正普通士兵/英雄走到近战位置后立即出手的问题，并按原版浮点比较保留首次命中的等待边界。完整英雄主脚本、全局伤害阶段和前三关至3-2的视频一致性仍未完成。

原版证据是 `all/script_utils.lua` 的 `soldier_move_to_slot_step` 和 `y_soldier_do_single_melee_attack`：

- 开始这一主脚本帧时已经在近战位置，移动函数才返回 false，允许接着选攻击。
- 这一帧才走到位置，移动函数仍返回 true。英雄到位并切换 idle 后，外层流程等待下一帧才开始攻击。
- 命中等待直接比较 `tick_ts - attack_start < hit_time`，不添加浮点容差。

网页原来按 `move()` 的返回值判断能否立即攻击；该返回值表示这一步移动后是否还未到达，因此把最后一步移动和攻击开始合并到了一帧。现在先比较本帧开始时的位置与近战位置，只要本帧需要移动就保留等待。首次命中比较也去掉了原版不存在的容差。

为区分“攻击开始早”与“命中等待短”，本轮给原始完整运行导出增加只读 `spriteTs` 字段，并重新执行原版 normal/constant 两种运行。原版泽菲拉在1315帧仍为 idle，1316帧才开始 attack_2，起点43.86666666666667；网页原起点43.833333333333336。修正后，双方都在1316帧出手、1331帧对同一个敌人造成8伤害。这不是把网页命中时间整体后移一帧。

验证：

- `export_hero_melee_arrival.lua` 执行原始移动函数和原始单次近战协程，导出72组/1,400帧：杰拉尔德两种基础攻击、泽菲拉基础攻击，6个出生时钟，距近战位置0/1/5/25像素，覆盖14次接近浮点边界却仍须等待的情况。网页逐帧位置、到位等待、攻击起点、首次伤害时间和值一致。这里攻击已预先指定，不验证选招、攻击完成或完整英雄主脚本。
- `verify_native_hero_melee.mjs` 在实际 GameSession 和完整原始同输入运行中，对照25个接敌/攻击状态、1316帧起点、1331帧8点伤害。
- `verify_native_combat_prefix.mjs` 扩展到1,352帧、18,876个存活敌人状态和4,011个已注册骑士状态，包含HP、位置、节点、数量、经济、生命、波次及骑士目标。并不覆盖全部注册表或音画一致性。
- 构建、完整自动化回归通过。浏览器实际第三关的受控静止敌人用例验证最后1像素到位时不出手、下一帧开始攻击、精确等待后造成8点伤害；泽菲拉合法暴击配装的近战/远程及引导、定期/pagehide存档恢复回归通过。截图为 `web-hero-melee-after-arrival.png` 和 `web-hero-melee-first-strike.png`。

新的首次实际战局偏差在1353帧的投石车爆炸。原版弹体487对敌人402造成14伤害；网页对对应敌人31造成15伤害。两者落点都是(649,430)。原版前一帧敌人位置(697.7288199321467,436.6812669985243)代入已验证的伤害公式得到14，本帧移动后位置(695.8572638904255,435.65735826538054)得到15；网页记录确实在后者位置计算。应继续追踪原版弹体与敌人的主脚本遍历次序，以及网页仍把普通弹体批量放在敌人移动后更新的问题。不能直接修改衰减公式来匹配某一发。

新开局捕获仍为2,055帧、4次投石车/12次法师射击、7,363个路径移动样本匹配。此对照指定敌人状态和顺序，不代表独立战局验收。六关固定策略结果写入 `hero-melee-playthrough.json`：1-1、1-2、2-1、3-1通关，2-2在131.2秒失败，3-2在109.633秒失败。相较上一轮，2-2该策略由胜转负；策略结果受修正后的战斗过程影响，不能作为回退到原版已证伪时序的理由，也不能替代完整还原验收。
