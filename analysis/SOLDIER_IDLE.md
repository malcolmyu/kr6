# 待机转身、等进度选敌与变化随机数对照

本轮移植原版士兵待机计时和转身，接入基础法师的空间查询与Lua排序，并修正由变化随机数暴露的投石车特效顺序和骑士回血初值。完整前三关至3-2、启动、实际听感与视频一致性仍未完成。

`all/script_utils.lua:2486` 的待机函数先切换到上一次选定的动画，再检查眩晕；连续待机计时累计超过cooldown时才抽取朝向和可选动画。间隔超过两个tick会清零计时，两个tick不清零。循环动画保留原时钟，数字1表示非循环，刚选出的动画从下一次调用生效。网页按这些规则实现，不用整秒计时器或额外容差。

实际主脚本需要区分几种到位/完成行为：回集结点的最后一步可以接着进入待机，走到近战位置的最后一步仍等待下一帧；远程攻击成功完成后同一帧可以继续待机。返回集结点时，原版在移动后决定朝向，目标位置恰好与移动后坐标相同的一帧会切换方向。原版walk还使用atan2、旋转单位向量、归一化与sqrt距离；直接除以距离或Math.hypot会在浮点边界产生不同的到位判断。本轮保留这些原始运算与分支。

变化随机数还暴露了两个独立问题：

- 投石车的原始顺序是伤害、落地文字、命中特效、贴花、payload。网页此前先创建特效，再创建文字，并提前排队payload；现在按原始主脚本顺序处理。
- 当多个敌人到终点的剩余节点数相同时，LuaJIT `table.sort`并不稳定。网页的稳定排序和创建顺序数组选中了不同的第二目标。现在基础法师查询使用sso5建立的格子和真实Lua实体表顺序，再运行原版分区/交换/递归排序；同tick移动更新对象位置，但不重建格子。这一连接目前不代表所有英雄、士兵与其他塔的空间查询都已移植。

骑士回血早了的问题来自 `regen.last_hit_ts` 的原版初值0，网页却使用负无穷。这会改变满血时已经运行的回血计时相位，并让后来本应死亡的骑士多出一次攻击。现在新单位使用模板中的last_hit_ts与ts_counter。没有增加额外的“到位前不计回血”规则。

验证：

- 原始待机函数315组、113400帧：英雄和骑士、三个出生时钟、五种随机输入，覆盖持续待机、两/三tick间隔、眩晕、强制时钟、数字非循环和可选动画，完整状态与调用顺序匹配。
- 原始LuaJIT排序606组、166624次比较，包含相同键、逆序和重复排序键；比较回调序列和最终对象顺序均匹配。
- 固定随机数完整用例1391帧、1815个实体事件、6781次随机调用；变化序列完整用例1391帧、1854个实体事件、6798次随机调用。真实GameSession的全局ID、完整实体表顺序、创建/排队/插入/删除、挂起队列、经济、生命、波次、败北与暂停均匹配，没有读取原版事件来驱动网页。
- 两组用例共38924个存活敌人状态、13821个士兵/英雄状态、13263个待机时钟与朝向匹配。士兵状态比较HP、位置和目标；待机状态另比较最后调用、累计时钟、动画与朝向。它们仍是指定操作的两段败北运行，不能替代完整3-2验收。
- 原版导出只增加待机状态/朝向只读观测，normal1899、constant1815、sequence1854个实体事件保持不变。构建和完整自动化测试通过。
