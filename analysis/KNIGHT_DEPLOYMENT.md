# 骑士出发、补员与死亡淡出

本轮修正骑士首次出发和集结时的等待、参与阻挡的时机、尸体淡出删除，以及兵营门未关闭时连续补员。完整前三关至3-2、视频画面和音效一致性仍未完成。

原始证据来自 APK 的 `kr6/scripts_game.lua:19635–19708`、`all/scripts.lua:1939–2021`、`all/script_utils.lua` 的 `y_soldier_death` 和 `fade_out_entity`，以及原版 health/tween/render 系统。骑士使用自己的集结协程，不能用通用 `SU.y_soldier_new_rally` 代替。反编译器错误地嵌套了一处分支；以下行为另用未修改的原始协程执行验证。

- 出发等待是 `队员序号 / 队员总数 * delay_max`，不抽随机数。等待期间禁止成为攻击目标，并按原版位掩码免疫伤害。
- 每个骑士首次等待结束后，只检查一次集结点附近是否有可阻挡敌人。此后走向集结点时，途中来敌不会持续触发这次检查。
- 等待中换集结点会重启等待；行走中换点仅改目的地。攻击中换点须经过原攻击中断和外层等待。
- 到达目的地的移动帧仍保持行走、禁选和免疫；下一主脚本帧才恢复。
- 死亡动画完成后，原版在骑士本体上添加淡出 tween。淡出按相对时间到达最后关键帧时就会请求删除，可能比 health 的严格 `delete_after < tick_ts` 早一帧。先前的独立死亡导出只运行 health/pops，遗漏了 tween；现已增加包含真实 tween 系统的独立证据，并让生产代码和验证使用此证据。
- 门开启后，其他空缺位置立即补员，不重置开门保持时间。关门动画结束后仍经过外层 yield，下一帧才可再次开门。

网页将普通骑士和四类基础敌人近战放入各自真实实体的 main 遍历位置；伤害在主脚本遍历之后结算。敌人预测使用该实体当前记录的运动速度，避免先把所有敌人移完再处理骑士。新骑士在排队创建帧尚不显示，实际入场帧才进入渲染。门和骑士尸体透明度也按原始动画帧及 tween 计算。

实际同输入运行中，原版骑士72在1249帧请求删除、1250帧删除；新骑士469在1260帧创建、1261帧入场。原版骑士71在1271帧请求删除、1272帧删除，门仍开着，因此474在1272帧立即创建、1273帧入场。网页现按相同帧执行这些语义事件，运行时全局ID仍因更早缺失实体而不同。

新捕获的开局对照仍为2,055帧、4次投石车射击、12次法师射击、7,363个原版路径移动样本一致。这些输入指定了敌人状态和顺序，不能作为独立完整战局或视频验收。六关固定策略试跑结果写入 `knight-deployment-playthrough.json`：1-1、1-2、2-1、2-2、3-1通关；3-2在110.433秒失败。这只是策略试跑。

下一处实际敌人状态差异是1330帧，网页敌人18（原版161）提前受到8点伤害。原始 damageTrace 显示泽菲拉58对此敌人的8点近战伤害在1331帧结算，网页只读调用追踪现也确认：1330帧是泽菲拉 `attack_2`，对敌人18将HP30直接改为22，施法起点为43.833333333333336。下一步应对齐英雄近战协程和伤害阶段，不能直接平移所有伤害。全局注册表首次差异仍在585帧；pops、血迹、其他死亡类型、全局伤害顺序和完整英雄主脚本尚未全部移植。真实播放的音效、启动效果及完整3-2仍未验收。
